# Background PDF text processing design

## Objective

Process previously extracted PDF text asynchronously. After a successful PDF upload, the server publishes a RabbitMQ message. The worker consumes it, splits the stored text into chunks, generates embeddings through OpenRouter, persists chunks and vectors in PostgreSQL with pgvector, and updates the document status.

This first version intentionally keeps the worker implementation small. It does not introduce Nest Microservices, an HTTP controller in the worker, retries, dead-letter queues, an outbox, or a layered worker architecture.

## Existing context

- The frontend extracts PDF text and sends it with the PDF.
- The server stores the PDF in R2.
- `Document` and `DocumentContent` are persisted together.
- New documents start with `Document.status = PROCESSING`.
- `DocumentContent.version` starts at `1`.
- `DocumentChunk` and `DocumentChunkEmbedding` already exist in the Prisma schema.
- The worker is a Nest application context and already connects to PostgreSQL, Redis, and RabbitMQ.

## Architecture

### Server publisher

The server will have one `DocumentProcessingPublisher` provider backed by `amqplib`. It will:

- connect using `RABBITMQ_URL`;
- assert the durable `document.processing` queue;
- publish persistent JSON messages;
- close its channel and connection during application shutdown.

After `UploadBotPdfUseCase` returns successfully, `UploadPdfBotController` publishes the document ID before returning the HTTP response.

Message contract:

```ts
interface DocumentProcessingMessage {
  documentId: string;
}
```

If publication fails after the document has been stored, the request returns an error and the document remains `PROCESSING`. Recovery through an outbox, republisher, or administrative command is outside this version.

### Worker consumer

The worker will have one `ProcessDocumentConsumer` provider. No HTTP controller will be added. The provider will contain three responsibilities in the same class for this initial implementation:

- initialize the queue and consumer in `onModuleInit`;
- validate and acknowledge RabbitMQ messages;
- process one document from start to finish.

The RabbitMQ channel will use `prefetch(1)`. Every received message will eventually be acknowledged. Processing failures will not be requeued.

## Processing flow

1. Parse the JSON message and validate that `documentId` is a non-empty string.
2. Query `document` joined with `document_content`.
3. If no record exists or the document is not `PROCESSING`, acknowledge the message and stop.
4. Split `DocumentContent.text` using LangChain's `RecursiveCharacterTextSplitter`:
   - chunk size: `1000` characters;
   - chunk overlap: `200` characters.
5. Generate embeddings through OpenRouter in batches of at most `50` chunks.
6. Validate that every returned embedding has exactly `1536` dimensions.
7. Start a PostgreSQL transaction.
8. Delete existing chunks for the same `documentId` and content version.
9. Insert `DocumentChunk` rows in chunk order.
10. Insert one `DocumentChunkEmbedding` per chunk.
11. Update the document status to `READY`.
12. Commit and acknowledge the RabbitMQ message.

If any processing step fails, the worker rolls back an active transaction, updates the document status to `FAILED`, logs the error without logging document text or the OpenRouter API key, and acknowledges the message.

## Embeddings

The first version uses fixed settings:

```ts
const EMBEDDING_MODEL = 'openai/text-embedding-3-small';
const EMBEDDING_DIMENSIONS = 1536;
const EMBEDDING_BATCH_SIZE = 50;
```

LangChain will provide:

- `RecursiveCharacterTextSplitter` from `@langchain/textsplitters`;
- `OpenAIEmbeddings` from `@langchain/openai`.

`OpenAIEmbeddings` will use the OpenRouter API key and the OpenAI-compatible base URL:

```text
https://openrouter.ai/api/v1
```

Only `OPENROUTER_API_KEY` is environment-specific. Model, dimensions, chunk size, overlap, and batch size remain constants so they cannot drift from the database type in this version.

## Database behavior

The embedding column will be changed from an unconstrained pgvector value to:

```prisma
embedding Unsupported("vector(1536)")?
```

A migration will alter the PostgreSQL column to `vector(1536)`. An HNSW index is intentionally deferred until semantic search is implemented.

The worker will use parameterized SQL through the existing `pg` pool. Prisma will not be introduced into the worker. Vector values will be passed as parameters and cast to `vector(1536)` by PostgreSQL.

For this version:

- `contentVersion` comes from `DocumentContent.version`;
- `chunkIndex` is zero-based and follows splitter output order;
- `tokenCount`, `pageStart`, and `pageEnd` are stored as `NULL`;
- chunk and embedding IDs are UUIDs generated by the worker;
- `model` stores `openai/text-embedding-3-small`;
- `dimensions` stores `1536`.

## Idempotency

Duplicate messages received after a document is `READY` or `FAILED` are acknowledged without processing. While a document is `PROCESSING`, processing replaces chunks for its current content version inside the same transaction.

This protects normal single-consumer delivery. Distributed locking for several worker replicas processing the same document concurrently is outside this version.

```

```

- `amqplib`;
- `@types/amqplib` as a development dependency.

New worker dependencies:

- `@langchain/core`;
- `@langchain/openai`;
- `@langchain/textsplitters`;

New worker development dependency and script:

- `vitest`;
- `test: vitest run`.

## Error handling

- Invalid RabbitMQ payload: log and acknowledge.
- Missing document/content: acknowledge without changing state.
- Document not in `PROCESSING`: acknowledge without changing state.
- OpenRouter, splitting, validation, or database error: mark `FAILED`, log, and acknowledge.
- Failure to mark `FAILED`: log both the original error and the status-update failure, then acknowledge.
- No automatic retries or dead-letter queue.

## Tests and verification

Automated tests will cover:

- publisher sends a persistent message to the expected durable queue;
- valid message loads content, creates ordered chunks, persists 1536-dimensional embeddings, and marks the document `READY`;
- chunks are generated with the configured size and overlap;
- existing chunks for the same version are replaced;
- missing or already processed documents are skipped and acknowledged;
- invalid messages are acknowledged without processing;
- embedding or database failure marks the document `FAILED` and acknowledges the message;
- no failed message is requeued.

Verification commands:

```bash
pnpm --filter server check-types
pnpm --filter worker check-types
pnpm --filter server test
pnpm --filter worker test
pnpm check-types
pnpm build
```

Tests will mock RabbitMQ and OpenRouter. They will not require a live OpenRouter API key.

## Out of scope

- semantic search and retrieval;
- HNSW or IVFFlat indexes;
- retries and exponential backoff;
- dead-letter queues;
- transactional outbox;
- worker HTTP endpoints;
- Nest Microservices transport;
- distributed processing locks;
- page metadata and token counting;
- reprocessing UI or administrative recovery;
- status progress percentages.
